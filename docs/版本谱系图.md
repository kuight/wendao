## 六、为什么不依赖版本号

修真分支和主分支存在**两套版本号体系**：

1. **修真分支**：从 v2.2 → v3.0 → v4.0 → v4.1-hotfix（CHANGELOG 都用「v4.x」修真线编号），其中 v3.0 比 v2.2「新」是正确的，但修真-v4.1 比修真-v3.0「新」也是正确的。**修真内版本号是线性递增的**。
2. **主分支**：从 v4.3.5f → v4.3.5g → v4.3.5h → v4.3.5i → v4.3.5j（小步快跑），再回到 v4.3.6 → v4.3.6a → v4.3.6b-p7（重置/重打版本）。主分支**版本号并不严格单调**——v4.3.5f (12:00) → v4.3.6 (09:47) → v4.3.6a (15:27) 这一天内三个不同版本共存，且 4.3.5f 的代码与 4.3.6 并不构成线性「升级」关系，而是「不同实验方向」。
3. **修真资产 × 主分支的版本号交叉**：修真-v4.1-hotfix (2026-07-03) 与主分支的 v4.3.6 (2026-07-05) 跨日，但修真资产随后被纳入主分支的 wendao4.4.0 (2026-07-22)。只看「v4.1 vs v4.3」会得出修真 < 主 的判断，但**修真资产实际进入了更晚的主分支版本**——这正是「不依赖版本号」的核心理由。

**以 mtime 为证据的好处**：
- mtime 由 zip 内**每一文件的实际修改时间**决定，不存在作者主观编号错误或重命名造成的影响。
- 当一个作者说「这是 v4.0 hotfix」但 mtime 显示是 2026-07-03，而另一作者说「这是 v4.3 final」但 mtime 显示是 2026-07-05，我们可以**直接按 mtime 排序**，不依赖任何「声明」。
- 在本项目中，mtime 与「修真/主分支归属」高度一致：修真分支所有节点的 mtime 都 ≤ 2026-07-03，主分支所有节点的 mtime 都 ≥ 2026-07-05；这一**mtime 分段**比版本号更可靠地刻画了两条分支的相对独立性。
- 完成度证据（如修真专属 JS 模块）独立于版本号存在；只要修真专属 JS 出现在哪个 zip，那个 zip 就属于修真影响范围。
